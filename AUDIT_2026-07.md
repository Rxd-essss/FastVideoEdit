> Аудит read-only: **ни одного файла не изменено**. Все находки — с точной привязкой
> `файл:строка` и процитированным кодом. Метод: 9 параллельных аудиторов по направлениям
> → адверсариальная верификация каждой находки отдельным «скептиком» → сведение.

> Статусы: **87 подтверждено** верификатором, **1 опровергнуто**, **20 не доверифицировано**

## 1. Итог одним абзацем

Ядро проекта инженерно крепкое (атомарная запись, дренаж stderr отдельным потоком,
виртуализация транскрипта, GPU-взаимоисключение, CSRF/TrustedHost). Но **пять ваших
симптомов сходятся к трём корневым причинам**, каждая из которых подтверждена кодом:

1. **Один общий «эффективный cutlist» не переиспользуется.** Субтитры, .srt, главы и enrich
   строятся по *одному* таймлайну, а видео рендерится по *другому* (короткие сегменты
   выкидываются уже внутри `render()`). Отсюда «субтитры съезжают» тем сильнее, чем длиннее видео.
2. **Гигантский `-filter_complex` уходит в командную строку инлайном.** На Windows это упирается
   в лимит ~32 767 символов при ~150+ вырезках → длинное видео падает *до* старта ffmpeg
   (`WinError 206`). Плюс результат рендера **никогда не валидируется** — ffmpeg вышел с кодом 0,
   файл объявлен готовым, даже если он обрезан. Это ровно «иногда роняет, иногда обрывается».
3. **Настройки и «Монтаж» рассинхронены между UI и бэком.** Модалка пересеивает поля из конфига
   при каждом открытии (выбор не живёт), очередь/watch-folder молча игнорируют половину настроек,
   а вкладка «Монтаж» читает схему `payload.visual`, которой у бэкенда нет — выбор кандидатов теряется.

Ничего из этого тесты не ловят: нет ни одного теста с **реальным** ffmpeg (везде `FakeFF`),
нет ни одного теста фронта (5000 строк JS), максимум **3 вырезки** в тестовых сценариях —
поэтому и краш на 150 сегментах, и рассинхрон субтитров невидимы для CI.

## 3. Разбор по вашим симптомам

### Симптом №1 — «Субтитры корявые»
Это не один баг, а стек из семи. P0-3 и P0-4 выше — главные. Остальные:

- **[HIGH]** [subtitles.py:438](vpipe/subtitles.py:438) — размеры стилей ASS заданы в **абсолютных пикселях**, а `PlayRes` = разрешению вывода. На 4K/1440p сабы вдвое мельче, на 480p — гигантские; в мультиформатном паке один пресет выглядит по-разному. *(enrich-cards масштабируются правильно, burn.ass — нет.)* Фикс: масштабировать `size/margin/outline` на `PlayResY/1080`, как в `enrich_cards._px`.
- **[HIGH ⚠️ не доверифи]** [probe.py:45](vpipe/probe.py:45) — **rotation-метадата игнорируется** (портрет с телефона): probe отдаёт до-поворотные размеры, ffmpeg авто-поворачивает кадр → ломается `PlayRes`, punch-zoom, логика пропуска дублей форматов.
- **[MEDIUM]** [subtitles.py:400](vpipe/subtitles.py:400) — karaoke выбрасывает переносы строк из `_wrap`: `max_lines=2` и русские правила переноса **не применяются** к прожжённым субтитрам.
- **[MEDIUM]** [subtitles.py:327](vpipe/subtitles.py:327) — kinetic-«поп» ключевого слова **не возвращает цвет**: слово остаётся янтарным до конца реплики.
- **[MEDIUM ⚠️]** [render.py:1174](vpipe/render.py:1174) — точки видео-реза не выровнены по кадровой сетке (аудио — сэмпл-точно) → дрейф «губы vs субтитры» случайным блужданием на сотнях склеек.
- **[LOW]** [subtitles.py:170](vpipe/subtitles.py:170) — принудительный 50мс зазор между репликами → «моргание» между каждой парой в непрерывной речи.
- **[LOW]** [subtitles.py:256](vpipe/subtitles.py:256) — `_ass_text_escape` использует несуществующие в ASS эскейпы → литеральные `\`/`{`/`}` в речи рендерятся мусором.
- **[LOW]** [enrich_cards.py:62](vpipe/enrich_cards.py:62) — геометрия панелей/CTA захардкожена под дефолтный стиль субтитров → пресеты «Неон»/«Крупный» налезают на сабы.

### Симптом №2 — «Длинные видео роняют / обрываются»
P0-1 (краш 32k) и P0-2 (нет валидации) — корень. Вокруг них — кластер lifecycle-дыр:

- **[MEDIUM]** [render.py:441](vpipe/render.py:441) — отмена работает только пока жив ffmpeg-процесс; в окнах measure/DFN/между проходами она **проглатывается**, GPU жжётся часами.
- **[MEDIUM]** [ffmpeg_utils.py:183](vpipe/ffmpeg_utils.py:183) — **нет watchdog/таймаута**: зависший энкод оставляет задачу «running» навсегда, все мутирующие эндпойнты отвечают 409 → приложение выглядит мёртвым.
- **[MEDIUM]** [render.py:581](vpipe/render.py:581) — DeepFilterNet-проход блокирующий, без прогресса и отмены → на часовом аудио бар замирает на ~30% на десятки минут (пользователь думает «завис»).
- **[MEDIUM ⚠️]** [serve.py:4461](serve.py:4461) — нет shutdown-хука: закрытие сервера при рендере **осиротит `ffmpeg.exe`** на Windows; следующий старт молча воюет со своими же залоченными `.part`.
- **[HIGH]** [badtakes.py:60](vpipe/detect/badtakes.py:60) + **[HIGH]** [serve.py:257](serve.py:257) — детект bad-takes **перезагружает qwen3:8b с диска в VRAM на каждое окно** (`keep_alive=0`), и вся детекция (LLM + Silero VAD по всему файлу) идёт **синхронно внутри HTTP-хендлера** `/api/open` — это тоже читается как «подвисание/краш».
- **[LOW]** [render.py:131](vpipe/render.py:131) — финальный `os.replace` вне `try`: залоченный целевой mp4 роняет часовой рендер на 100% и оставляет многогиговый `.part`.
- **[LOW]** [ffmpeg_utils.py:198](vpipe/ffmpeg_utils.py:198) — в `task.error` зашивается весь граф (до ~30КБ) → заливает SSE и делает тост-ошибку нечитаемой.
- **[LOW ⚠️]** [censor.py:88](vpipe/censor.py:88) — censor-графы тоже растут линейно (asplit=N по каждому слову) → тот же лимит 32k на матерных видео.

## 4. Сквозные направления

### Краевые случаи (не учтены)
Rotation-метадата (portrait), HDR/10-bit, апостроф в имени, мульти-аудиодорожка ([probe.py:93](vpipe/probe.py:93) — транскрибируется не та дорожка, что рендерится), NaN/Infinity в cutlist, cut за EOF ([timeline.py:89](vpipe/timeline.py:89) не клампит старт), watch-folder на залоченном файле ([serve.py:1765](serve.py:1765) — регистрируется как обработанный после первой ошибки, не ретраится), очень короткие видео (<~55с — [enrich.py:1205](vpipe/enrich.py:1205) clean-zone авто-режектит все предложения, без объяснения в UI).

### Производительность / плохая оптимизация
- **[MEDIUM]** [serve.py:1435](serve.py:1435) ⚠️ — мультиформатный рендер **переганяет весь аудио-пайплайн** (censor FLAC, DeepFilterNet, 2-pass loudnorm) и face-detection **на каждый формат**, хотя артефакты идентичны. Считать один раз, переиспользовать.
- **[MEDIUM]** [imagegen.py:263](vpipe/imagegen.py:263) — SD спавнит новый процесс на **каждую** картинку, перезагружая ~4ГБ SDXL-Turbo с диска (4 кандидата × каждая точка). Батч-режим `sd-cli -b N`.
- **[MEDIUM]** [enrich_llm.py:843](vpipe/enrich_llm.py:843) — CTA-детектор шлёт **весь** размеченный транскрипт одним промптом → на 50+ мин превышает `num_ctx=16384`, Ollama молча обрезает.
- **[MEDIUM ⚠️]** [hesitations.py:155](vpipe/detect/hesitations.py:155) — два полных линейных прохода по всем словам на **каждый** VAD-гэп → O(гэпы×слова).
- **[LOW]** [serve.py:2212](serve.py:2212) каждая правка слова переписывает весь многомегабайтный транскрипт синхронно; [serve.py:2085](serve.py:2085) блокирующая запись аплоада в async-хендлере стопит event loop; [serve.py:4424](serve.py:4424) ⚠️ / [serve.py:2070](serve.py:2070) — **нет эвикшена кэшей** нигде (enrich_img, codegfx, peaks, _uploads, work-дир растут безгранично); [transcribe.py:294](vpipe/transcribe.py:294) whisper грузится с диска на каждую задачу.

### Качество тестов — почему баги проходят
- **[CRITICAL ⚠️]** [test_edge_fade.py:79](tests/test_edge_fade.py:79) — **нет ни одного теста с реальным ffmpeg**: все render-тесты пинят строки графа против `FakeFF`, CI явно банит бинарь, единственный медиа-фикстур осиротел. Отсюда невидимость краша 32k и обрыва вывода.
